# mm-catalog-api

## Архив материалов

Архив материалов хранится в одной отдельной таблице `catalog.archive_materials` с теми же полями и связями со справочниками. Изображения и связи с кромками остаются в общих таблицах `material_images`, `material_edge_links` и `material_edge_link_markings`. Перенос в обе стороны выполняется одной транзакцией: у существующих изображений и связей переключаются nullable-ссылки `material_id` и `archived_material_id`; сами строки и их маркировки не копируются. У связей и маркировок есть собственные независимые первичные ключи `id`. Вычисляемый `owner_material_id = COALESCE(material_id, archived_material_id)` сохраняет дополнительный ключ владельца связи `(Id материала, Id кромки)` для прежней ссылки маркировок, поэтому существующие поля маркировок не переписываются. Сохраняются Id материала, Id/GUID изображений, Id связей и маркировок, справочники, кромки, порядок кромок и маркировки связей. В архивной записи `original_material_id` сохраняет исходный Id отдельным числовым полем без FK к основной таблице; при восстановлении материал получает этот Id. Id архивной записи также сохраняется равным исходному Id. В архив материал добавляется в конец списка. При переносе сохраняется `original_order_by_col`; при восстановлении материал возвращается на сохранённую позицию основного списка. Если её заняла другая запись, она и следующие записи сдвигаются на одну позицию с сохранением взаимного порядка. Свободная позиция используется без перестановки остальных материалов. Поле `original_order_by_col` обязательное: для новых переносов оно всегда содержит фактическую позицию материала перед архивированием. Для ранее существовавших архивных записей миграция создаёт значение `0`; их исторические позиции автоматически не восстанавливаются и данные архива не удаляются. Активные и архивные материалы имеют независимый порядок; обычные списки сайта, ЛК и выбора материалов для расчёта читают только активную таблицу.

`GET /api/for-admin/materials/archive` и `/archive/compact` возвращают архив с теми же DTO и фильтрами, что основные списки. `POST /api/for-admin/materials/{id}/archive` и `POST /api/for-admin/materials/{id}/restore` без тела возвращают `{ "success": true }`. Повтор уже выполненного переноса допустим. Карточка по прежнему Id доступна через общий `GET /api/for-admin/materials/{id}` и содержит `isArchived`. Общие операции изменения, удаления, внешней ссылки и сортировки работают с обеими таблицами по тому же Id. Клонирование доступно только актуальным материалам. Синхронизация со Стройдвором доступна только актуальным материалам; архив сохраняет ранее полученные данные поставщика.

`POST /api/for-admin/materials/export` принимает `isArchived`: по умолчанию `false` выгружает активные материалы, `true` — архив. Переданные `ids` должны относиться к выбранному списку. У архивного файла имя `archive-materials.xlsx`.

Миграции `20261107133901_AddMaterialArchive` и `20261107141525_AddArchivedMaterialOriginalOrder` пользователь применяет вручную перед запуском обновлённых API и фронтенда; агент не применяет их к БД. Вторая миграция добавляет только обязательный `original_order_by_col` со значением `0` для существующих строк, без SQL переноса данных и автоматического определения исторической позиции. Перед откатом миграции все архивные материалы нужно вернуть в основной список.

## Каталог кромок

CRUD кромок и справочников производителей, толщин и единиц продажи расположен под `/api/for-admin/edges`. Список кромок вместе с фильтрами возвращается одним запросом `GET /api/for-admin/edges/compact`. Изображения загружаются через административный API кромок и читаются через `/api/edges/images/{fileGuid}`. Общий порядок материалов и кромок, перемещение стрелками и миграция `20261025151403_AddEdgeSortOrder` описаны в [CATALOG_ORDER.md](catalog-api/docs/CATALOG_ORDER.md).

Контракты и правила описаны в [docs/EDGES_API.md](catalog-api/docs/EDGES_API.md). Миграция `20261022200130_AddEdgesCatalog` создаёт шесть отдельных таблиц кромок без тестовых данных. Миграцию применяет пользователь вручную; перед применением нужно проверить ожидающие миграции и целевую БД. Изменения не подключают прототип Front к API автоматически.

Сборка без обращения к NuGet: `dotnet build catalog-api/catalog-api.slnx --no-restore`. Зависимости для этого этапа не менялись.

### Размеры кромок

Справочник называется `EdgeSize`: сущность, DTO и операции используют это имя; таблица — `catalog.edge_sizes`, связь кромки — `sizeId` (`catalog.edges.size_id`), компактные фильтры — `filters.sizes`. Административные операции доступны по `/api/for-admin/edges/sizes`, страница Catalog Front — `/edge-sizes`. Поля размера `thickness` (толщина), `width`, `name` и `orderByCol` сохраняются; поля толщины материалов не меняются. Названия размеров могут повторяться; уникальна только пара `thickness` + `width`. Для `EdgeSize` нет вычисляемого `NormalizedName` и ограничения уникальности имени.

Перед обновлением API и Front пользователь применяет миграцию `20261113232428_RenameEdgeThicknessToEdgeSize`. Она переименовывает таблицу, колонку связи `thickness_id` в `size_id`, колонку размера `value` в `thickness`, индексы и ограничения без пересоздания таблицы и потери ID, размеров, порядка или связей, а также удаляет вычисляемый `normalized_name` и его уникальный индекс. Обратная миграция возвращает прежние имена и уникальность нормализованного названия; перед откатом потребуется устранить появившиеся повторы названий. История использует строковый идентификатор `EdgeSize`.

### Ширина и название кромки

В справочнике размеров кромок хранится обязательное поле `width` — ширина в миллиметрах, положительное число до трёх знаков после точки. Запись содержит произвольное название `name`, толщину `thickness` и ширину `width`; уникальна пара толщины и ширины. Можно завести несколько записей с толщиной `1` и разной шириной, например `19` и `25`, и выбирать нужную через поле кромки `sizeId`. Ширина доступна в карточке и списке справочника, фильтрах компактного списка, истории и Excel-экспорте кромок. Для существующих записей миграция устанавливает переходное значение `0`; при создании или изменении размера требуется положительная ширина.

`GET /api/for-calculate/edges/price` возвращает полное название выбранной кромки в поле `name`: `Кромка {название} {название размера}`. Название размера берётся из `EdgeSize.Name`; числовые `thickness` и `width` в имя не подставляются. Пробелы по краям обоих названий убираются, внутреннее написание сохраняется. Артикул отдельно в название не добавляется. Суффикс ` (Склад)` добавляется только при `isStockItem=true`, независимо от остатка. Например, при названии размера `1 мм / 19 мм` результат — `Кромка Кашемир серый U702 ST9 1 мм / 19 мм (Склад)`.

Перед обновлением API пользователь вручную применяет миграцию `20261112181213_AddEdgeThicknessWidth`. Она добавляет обязательный столбец `catalog.edge_thicknesses.width` типа `numeric(18,3)` со значением по умолчанию `0` и заменяет уникальность толщины уникальностью пары толщины и ширины. Откат удаляет поле вместе с введёнными значениями ширины и требует предварительно устранить повторяющиеся толщины. Catalog API и Catalog Front обновляются согласованно.

## Порядок размеров кромок

Административные список и карточка размера кромок возвращают `orderByCol`. Список `/api/for-admin/edges/sizes` и `filters.sizes` ответа `/api/for-admin/edges/compact` сортируются только по этому полю. Новая запись добавляется в конец; изменение названия, толщины или ширины сохраняет её позицию.

`POST /api/for-admin/edges/sizes/change-order-col` принимает `{ "id": 1, "direction": "UP" }` или `"DOWN"` и переставляет соседние записи полного списка. Ответ — `{ "success": true }`; перемещение за границу возвращает `400`. Создание и перестановка выполняются через EF Serializable с существующим повтором конфликтов. Перестановка записывается в историю как изменение размера кромок; для тестера история не создаётся. После перемещения клиент перечитывает список и обновляет кэш кромок.

Миграция `20261113170651_AddEdgeThicknessSortOrder` добавляет `catalog.edge_thicknesses.order_by_col` с `NOT NULL DEFAULT 0` и индексом `(order_by_col, id)`. Пользователь применяет её вручную до запуска обновлённого API. Существующие размеры получают нулевые позиции; порядок записей с одинаковым `orderByCol` не определён. Первое успешное перемещение нормализует позиции в `1..N` по прочитанному списку с учётом запрошенной перестановки. SQL-переноса данных нет. Откат удаляет только новый столбец и индекс вместе с сохранённым порядком.

## Порядок маркировок связей

У маркировки есть необязательное поле `description` до 2000 символов. Оно сохраняется при создании и изменении, возвращается в карточке, списке маркировок и `filters.markings` компактного списка связей. Пустое или пробельное описание сохраняется как `null`; существующие маркировки остаются без описания.

Перед запуском обновлённого API пользователь вручную применяет миграцию `20261106140752_AddRelationMarkingDescription`. Она добавляет nullable-столбец `catalog.relation_markings.description`; откат удаляет этот столбец вместе с описаниями.

Маркировки возвращаются только по `orderByCol` в списке `/api/for-admin/relations/markings` и `filters.markings` компактного списка связей. Поле `orderByCol` также есть в карточке. Новая маркировка добавляется в конец; переименование сохраняет её позицию.

`POST /api/for-admin/relations/markings/change-order-col` принимает `{ "id": 1, "direction": "UP" }` или `"DOWN"` и возвращает `{ "success": true }`. Переставляются соседи полного списка, независимо от фильтра клиента; на границе возвращается `400`. После изменения клиент перечитывает список и инвалидирует кэш связей. Создание и перемещение выполняются через EF Serializable с существующим повтором конфликтов. Перемещение записывается в историю как Update маркировки; для tester действует стандартный пропуск истории.

Миграция `20261025173751_AddRelationMarkingSortOrder` добавляет `catalog.relation_markings.order_by_col` с `NOT NULL DEFAULT 0` и индексом `(order_by_col, id)`. Её применяет пользователь вручную до запуска новой версии API. Существующие маркировки получают нулевые значения; порядок записей с одинаковым `orderByCol` не определён. Первое успешное перемещение нормализует позиции в `1..N` по прочитанному списку с учётом запрошенной перестановки. Миграция не содержит SQL переноса данных; откат удаляет только новое поле и индекс.

## Стоимость кромки

У кромки есть обязательное поле `price` — стоимость в рублях за метр при `EdgeSaleUnit.SaleUnitType = Meter` или за целую бухту при `Roll`. Существующие значения цен не пересчитываются автоматически. Поле доступно при создании и изменении, в карточке, компактном списке, Excel-выгрузке и истории. Отсутствие поля и `null` отклоняются; ноль допустим. Контракт и миграции `20261026093511_AddEdgePrice` / `20261026100653_RequireEdgePrice` описаны в [EDGE_PRICES.md](catalog-api/docs/EDGE_PRICES.md).

Начальная загрузка берёт эффективную цену «Мебельщик» из ВЕК. [Сверка и результаты переноса](catalog-api/docs/edge-prices-2026-10-26/result.md) содержат источники, решения по расхождениям и проверки.

По последующему указанию пользователя 26.10.2026 M703/M715/M801 получили стоимость 0, а миграция `RequireEdgePrice` применена к `mm`. Все 396 стоимостей заполнены; `PriceSpecified` удалён. [Проверка обязательной стоимости](catalog-api/docs/edge-prices-required-2026-10-26/result.md).

## Удаление кромки со связями

`DELETE /api/for-admin/edges/{id}` отклоняет удаление кромки при любой связи с материалом: `400 ProblemDetails` с сообщением «Кромка связана с материалами. Сначала снимите все связи с материалами.». Сначала нужно удалить все её связи; после этого кромка удаляется обычным способом вместе с изображениями.

Миграция `20261026062250_RestrictLinkedEdgeDeletion` меняет FK `material_edge_links.edge_id → edges.id` с Cascade на Restrict. Пользователь применяет её вручную. Эта защита БД закрывает гонку появления связи между проверкой и удалением: нарушение именно этого FK преобразуется в то же сообщение `400`, а не удаляет связь каскадно. Проверка без применённой миграции не даёт полной защиты от такой гонки. Поведение удаления материала и очистки его связей не меняется.

## Удаление старых артикулов кромок

Раздел «Старые артикулы кромок», административный API соответствий и преобразование артикула для выгрузки в 1С удалены. Компактный список кромок больше не содержит `oldArticles`.

Перед обновлением API пользователь вручную применяет миграцию `20261105181604_RemoveEdgeArticleReplacements`. Она удаляет таблицу `catalog.edge_article_replacements` с её данными. Откат восстанавливает только структуру таблицы, без удалённых соответствий. Защита от удаления кромок со связями с материалами сохраняется.

## Порядок единиц продажи кромок

Административные список и карточка единицы продажи возвращают `orderByCol`; список сортируется только по этому полю. Новая запись добавляется в конец; изменение её полей не сбрасывает сохранённый порядок. `POST /api/for-admin/edges/sale-units/change-order-col` принимает `{ "id": 1, "direction": "UP" }` или `"DOWN"` и переставляет соседние записи полного списка. Ответ — `{ "success": true }`; перемещение за границу возвращает `400`. Перестановка записывается в историю как изменение единицы продажи; для тестера история не создаётся.

Тот же порядок используется в `filters.saleUnits` ответа `/api/for-admin/edges/compact`, из которого редактор кромки строит выпадающий список.

Перед запуском обновлённого API пользователь вручную применяет миграцию `20261112110509_AddEdgeSaleUnitSortOrder`. Она добавляет `catalog.edge_sale_units.order_by_col` с `NOT NULL DEFAULT 0` и индексом `(order_by_col, name, id)`. Существующие записи получают нулевой `orderByCol`; порядок записей с одинаковым значением не определён. Первое перемещение нормализует позиции в `1..N` по прочитанному списку с учётом запрошенной перестановки. SQL-переноса данных нет. Откат удаляет новое поле и индекс вместе с сохранённым порядком.

## Документация API

У типа материала есть флаг `hideOnSite` («Скрыть на сайте»): административные создание, изменение, карточка и список читают и сохраняют его, изменения записываются в историю. Значение по умолчанию — `false`. Скрытый тип исключается из публичного меню `/api/materials/material-types` и фильтров; его материалы исключаются из публичного списка, поиска, карточек и счётчиков фасет. Явный фильтр по скрытому типу возвращает 400, как для скрытой категории. Собственные флаги материалов не меняются: после снятия скрытия возвращаются только материалы, видимые по своим настройкам и настройкам категории. Административный каталог, ЛК и Calculate API не зависят от этого флага типа.

Перед запуском обновлённого API пользователь применяет миграцию `20261103175422_AddMaterialTypeSiteVisibility`. Она добавляет `catalog.material_types.hide_on_site` со значением `false` для существующих типов; при откате удаляется только этот столбец. Типы, которые нужно скрыть, выбираются в Catalog Front после применения миграции.

Настраиваемая выгрузка материалов и кромок в `.xlsx`: [контракт экспорта](catalog-api/docs/EXCEL_EXPORT_API.md).

`GET /api/for-vek-lk/materials` для авторизованного пользователя ЛК возвращает `{ "items": [{ "id", "name", "article", "categoryId", "count", "image" }], "categories": [{ "id", "name" }] }` для выбора материала в раскрое. Включаются материалы, у которых и у категории `hideInLk=false`, независимо от `hideOnSite`; категории без доступных материалов отсутствуют. `name` формируется как «тип материала → название → толщина в мм → высота×ширина плиты → производитель», например `ЛДСП Айрон Рок U9712 LF 16 мм 2750×1830 Увадрев`. Дробная толщина выводится без лишних нулей, с десятичной запятой. Материалы с нулевым остатком остаются в выдаче. Категории упорядочены только по своему `orderByCol`; материалы — в порядке категорий, внутри категории только по собственному `orderByCol`. `image` содержит GUID миниатюры 240 px, при её отсутствии — 480 px, иначе null; изображение доступно через `GET /api/materials/images/{guid}`. Все Id принадлежат Catalog API. В профиле Vek запрос требует cookie `VekExpressCookie`; фронт передаёт её через `credentials: "include"`. Без действительной cookie возвращается 401.

`GET /api/for-vek-lk/materials/{id}` возвращает только `{ "id", "name" }` выбранного материала с теми же правилами авторизации, видимости и форматом имени. Неизвестный материал, скрытый материал или материал скрытой категории возвращает `400 ProblemDetails`.

`hideInLk` — отдельный признак материала и категории, доступный в административных запросах создания/обновления, карточках и списках. У материалов он также копируется при клонировании и доступен в Excel-экспорте. `true` означает «скрыт в ЛК», как у `hideOnSite`; значение по умолчанию — `false`. При сохранении записывается значение поля из модели. `hideInLk=true` у категории скрывает её материалы в ЛК, не меняя собственные флаги этих материалов; снятие признака возвращает только материалы с `hideInLk=false`. Настройки сайта остаются независимыми.

Все материалы каталога предназначены для раскроя. Поля `applicableToCutting`, `applicableToPvhFacades`, `applicableToEnamelFacades`, их компактные варианты `cu`/`pv`/`en`, enum `MaterialCalculatorEnum` и query-параметр `calculators` удалены из актуальных контрактов.

Перед запуском обновлённого API пользователь применяет миграцию `20261030105853_AddLkVisibilityAndRemoveMaterialApplicability`. Она добавляет `hide_in_lk=false` для всех существующих материалов и категорий и удаляет три прежних столбца назначения. При откате эти столбцы создаются со значением `false`; прежние значения не восстанавливаются.

`GET /api/for-admin/materials/compact` возвращает в поле `im` GUID миниатюры 240 px, при её отсутствии — 480 px, иначе null. Оригинал не подставляется. Список читает только GUID; файл можно лениво получить через публичный `GET /api/materials/images/{guid}` с годовым HTTP-кешем и ETag по GUID.

Поле `el` компактного списка содержит внешнюю ссылку материала или null. `PUT /api/for-admin/materials/{id}/external-link` с `{ "externalLink": "https://example.com/material" }` меняет только эту ссылку; null или пустая строка удаляют её. Разрешены полные HTTP(S)-ссылки до 250 символов. Ответ — `{ "success": true }`.

`POST /api/for-admin/materials/{id}/clone` без тела возвращает `{ "newMaterialId": 123 }`. Копия получает название «исходное название (Копия)» и место сразу после исходного материала в общем порядке. Копируются все свойства, изображения с новыми GUID, связи с кромками и их маркировки; общие кромки и справочники остаются прежними. В истории создаётся одна запись Create с источником копии. Для названия длиннее 250 символов после добавления суффикса возвращается 400. Изменения схемы БД не требуются.

`ApiDoc:Enabled` включает OpenAPI, Scalar и Swagger UI. В `appsettings.json` документация выключена, в `appsettings.Development.json` включена. Если флаг отсутствует, документация недоступна. Для включения в другом окружении задайте `ApiDoc__Enabled=true` и перезапустите API.

Одиночный `POST /api/for-admin/materials/{id}/stroydvor/sync` возвращает `200` только при успешной синхронизации. Неуспешный результат возвращается как `400 ProblemDetails` с причиной в `detail`, после сохранения изменений снимка поставщика. Клиент перечитывает карточку материала для актуальной цены, наличия и даты синхронизации.

Привязка к Стройдвору доступна для справочных типов `ЛДСП` и `ЛМДФ` любой толщины и в любой категории. Тип определяется по `MaterialType.Name`, а не по названию позиции; `МДФ` не считается синонимом `ЛМДФ`. Допускаются также точные латинские обозначения `LDSP` и `LMDF`. Сохраняются пары производителя и формата: Увадрев (id 3) — 2750×1830; Swiss Krono (id 5) — 2750×1830 или 2800×2070; Ultradecor (id 2) и Egger (id 7) — 2800×2070. Поворот листа допустим.

Тип поставщика берётся из первого отдельного слова заголовка основной карточки товара, независимо от раздела сайта Стройдвора. Он должен точно совпадать с нашим справочным типом. Несовпадение сообщает оба типа, сбрасывает цену поставщика в 0 и очищает дату синхронизации. Проверки толщины и формата по данным карточки сохраняются. Изменение типа, привязки или данных материала во время запроса не позволяет записать устаревший снимок.

## Подключения к БД и общая авторизация

CORS сохраняет разрешение основного домена и поддоменов и дополнительно принимает точный iOS-origin `capacitor://localhost` для публичного мобильного каталога. Регистрация `AddMobileClientCors` находится в Core. Административные методы и ВЕК ЛК продолжают использовать cookie-авторизацию.

`DbConnString` задаёт подключение к данным Catalog API. `DataProtectionDbConnString` задаёт отдельное подключение к общему хранилищу ключей Data Protection, которыми защищаются cookie авторизации; сами cookie в этой БД не хранятся. Строки подключения независимы: хост, база, пользователь и остальные параметры могут различаться.

Для общей авторизации с Accounts API должны совпадать хранилище ключей, имя приложения Data Protection (`Cookie.CookieName(Cookie.DomainName)`), имя cookie и её домен. `DataProtectionDbConnString` должен указывать на хранилище Accounts API, выдавшего cookie.

Оба подключения задаются в `appsettings.json` и `appsettings.Development.json` либо одноимёнными переменными окружения. После изменения строк подключения перезапустите API; перекомпиляция не требуется.

`Authentication:Provider` выбирает только провайдер БД ключей: `Accounts` — прежний PostgreSQL по умолчанию, `Vek` — MS SQL ВЕК. Cookie-авторизация и существующие проверки ролей остаются общими. ВЕК выпускает совместимую cookie; PostgreSQL с данными каталога остаётся отдельным подключением.

Catalog API использует `Microsoft.Data.SqlClient 7.1.1` без необязательного пакета Azure-аутентификации. `SatelliteResourceLanguages=en` исключает языковые сборки зависимостей из build/publish; русские сообщения самого API сохраняются. Публикацию выполняйте в чистую папку, чтобы в ней не оставались файлы предыдущих зависимостей.

## Публикация Main и Vek

Два профиля публикации в папку можно выбрать в IDE или запустить из корня репозитория:

```bash
dotnet publish catalog-api/Catalog.Api/Catalog.Api.csproj -c Release --no-restore -p:PublishProfile=Main
dotnet publish catalog-api/Catalog.Api/Catalog.Api.csproj -c Release --no-restore -p:PublishProfile=Vek
```

| Профиль | Папка результата | Источник опубликованного `appsettings.json` |
| --- | --- | --- |
| [Main](catalog-api/Catalog.Api/Properties/PublishProfiles/Main.pubxml) | `catalog-api/Catalog.Api/bin/Publish/Main/` | `appsettings.json` |
| [Vek](catalog-api/Catalog.Api/Properties/PublishProfiles/Vek.pubxml) | `catalog-api/Catalog.Api/bin/Publish/Vek/` | `appsettings.Vek.json` |

В папке `Vek` опубликованный `appsettings.json` содержит точную копию `appsettings.Vek.json`. Это полный конфиг, а не дополнение к основному. Редактируйте настройки ВЕК в этом JSON и повторяйте команду.

Окружение приложения остаётся `Production` по умолчанию; задавать `ASPNETCORE_ENVIRONMENT=Vek` не требуется. Исходные JSON и конфигурация локальной сборки не меняются. Обычный publish без профиля использует основной `appsettings.json`; `appsettings.Development.json` и отдельный `appsettings.Vek.json` не публикуются. При повторной публикации основной файл настроек перезаписывается выбранным вариантом.

## Диагностика локальной разработки

### Сборка и форматирование в sandbox

Если `dotnet build` или `dotnet format` зависает после запуска либо завершается ошибкой Roslyn `named pipe` / `Permission denied`, проверьте вывод и принадлежность процесса. Остановите только собственный зависший процесс и повторите команду через штатное разрешение на выполнение вне sandbox. Не останавливайте процессы пользователя и не меняйте постоянные порты или `hosts` ради проверки.

Обязательную проверку `dotnet format catalog-api/catalog-api.slnx --verify-no-changes --no-restore` выполняйте из корня репозитория. Если она обнаруживает ранее существовавшие нарушения вне задачи, отдельно проверьте изменённые файлы через `--include` и сообщите об ограничении общей проверки. Не правьте подмодуль `core` ради посторонних ошибок форматирования без предусмотренного правилами согласования.

### Ошибка PostgreSQL 42703 после переименования поля

Ошибка `42703` о недостающем переименованном столбце может означать, что приложение обновлено, а схема БД ещё нет. Сначала сверяйте подключение с нужным окружением и просматривайте историю через `dotnet ef migrations list --project catalog-api/Catalog.Database/Catalog.Database.csproj --context CatalogDbContext`. У design-time factory собственная строка подключения: одно значение `ASPNETCORE_ENVIRONMENT=Development` не гарантирует выбор нужной БД. Сравнивайте настройки без вывода секретов. Factory поддерживает переменную окружения `DbConnString`; если она не задана, используется прежнее подключение по умолчанию. Перед любыми EF-командами для локальной разработки, особенно `dotnet ef migrations remove` без опции `--connection`, обязательно задавайте `DbConnString` с `Database=mm-debug` и проверяйте целевую БД. Не передавайте `--force` для удаления неприменённой миграции.

Применяйте миграции согласно `AGENTS.md`: по умолчанию это делает пользователь вручную. Агент может отступить от запрета только по явному разрешению пользователя для конкретных миграций и БД; перед применением проверьте весь список ожидающих миграций и задайте точную целевую миграцию. После применения проверьте историю и повторите затронутый запрос чтения. Не переписывайте исторические миграции и не создавайте недостающие столбцы вручную.

## Размеры материала

Материал ссылается на формат плиты через `sheetSizeId`. Поля `kvM` и `perimetrM` удалены из модели, административных запросов создания/обновления и ответов API. `GET /api/for-calculate/materials/{id}` возвращает `{ "id", "width", "height", "price", "name", "article" }`; ширина и высота берутся из формата плиты и выражены в целых миллиметрах, `price` — стоимость листа в рублях. `name` использует общий шаблон полного имени для ЛК: тип материала, название, толщина, формат плиты и производитель.

Миграция `20261019214841_RemoveMaterialMeasurements` удаляет столбцы `kv_m` и `perimetr_m` из `catalog.materials`. Её применяет пользователь вручную после подготовки потребителей нового контракта. При откате миграция восстанавливает столбцы с нулями, а не прежние значения. До обновления модели БД создание материалов новой версией API не проверяется.

## Стоимость для Calculate API

`GET /api/for-calculate/edges/price?materialId=123&thickness=0.4` возвращает `{ "price": 25.50, "article": "M-123", "name": "Кромка Ярко-серая U750 ST9 0.4/19", "quantityMultiple": 5, "saleUnitType": "Meter" }` — стоимость, артикул, полное название, кратность в метрах и тип продажи кромки. Поле `name` формируется через `EdgeNameHelper` из названия кромки и `EdgeSize.Name`; суффикс ` (Склад)` добавляется при `isStockItem=true`, артикул отдельно в имя не добавляется. `quantityMultiple` передаёт существующую `EdgeSaleUnit.Length`: для `Meter` это кратность отреза, для `Roll` — длина бухты; значение положительное, до трёх знаков после запятой. Calculate API применяет правило к общему расходу выбранной кромки с технологическим запасом. Для `Meter` количество равно `Ceiling(расход / quantityMultiple) * quantityMultiple` метров: 3 м при кратности 5 оплачиваются как 5 м по цене метра. Для `Roll` число оплачиваемых бухт равно `Ceiling(расход / quantityMultiple)`, сумма — число бухт, умноженное на цену бухты: 23 м при длине 200 оплачиваются как одна бухта. В строке расчёта `quantity` и `originalQuantity` остаются в метрах, поэтому для этого примера начисленное количество равно 200 м. Нулевой расход даёт нулевое количество. Толщина передаётся значением в миллиметрах, а не Id справочника. По умолчанию выбирается связь указанного материала с кромкой нужной толщины без фильтра по маркировке. Для расчётов ВЕК Calculate API передаёт `forVek=true`: дополнительно требуется маркировка «Век ЛК». Кратность и тип продажи передаются одинаково в обоих случаях. Если подходящей связи нет или их несколько, возвращается `400 ProblemDetails` с указанием толщины; маркировка упоминается только при `forVek=true`. Ошибочные параметры и неизвестный материал также отклоняются. Нулевая цена найденной кромки допустима. Endpoint доступен анонимно, как получение одного материала для расчёта. Catalog API, Calculate API и административный фронтенд обновляются согласованно, чтобы тип продажи одинаково определял единицу цены и расчёт суммы.

Количество листов, расход кромки и технологический запас рассчитывает Calculate API. Миграции для новых контрактов Catalog API не требуются; поле стоимости кромки должно уже присутствовать в БД.
