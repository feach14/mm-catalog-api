# Инструкции для AI-агентов

## Организация разработки Catalog API

- Размещайте прикладную логику вертикальными срезами в `catalog-api/Catalog.Api/Features`: запрос или команда, результат, валидатор и handler должны находиться рядом в соответствующей предметной фиче.
- Операции чтения оформляйте через `IQuery<TResult>` и `IQueryHandler<TQuery, TResult>`, операции изменения — через `ICommand<TResult>` и `ICommandHandler<TCommand, TResult>`.
- Контроллеры должны оставаться тонкими: принять и связать HTTP-параметры, передать сообщение соответствующему handler и вернуть результат. Не переносите в контроллеры запросы к БД и прикладную логику.
- Handlers регистрируются автоматически через `AddFeatures`, а валидаторы — через `AddFluentValidation`; не добавляйте их вручную в DI.
- Для запросов к EF Core используйте асинхронные методы и передавайте полученный `CancellationToken`. Для read-only запросов используйте `AsNoTracking`, если отслеживание сущностей действительно не требуется.
- Не вводите repository/service-обёртки только ради дополнительного слоя: существующие handlers работают непосредственно с `CatalogDbContext` и инфраструктурными зависимостями.

## Оформление атрибутов

- Атрибуты, относящиеся к одному объявлению, объединяйте в одну секцию `[...]`, если это допускает C#. Не создавайте отдельную пару квадратных скобок для каждого атрибута.
- Если список атрибутов метода не помещается в одну строку, оставляйте одну общую секцию и переносите отдельные атрибуты внутри неё на следующие строки.
- Обычный атрибут без явного target `property:` можно располагать строкой над свойством или параметром. Например, для свойства обычного класса допустима запись атрибута `Description` над объявлением свойства.
- Для positional property record атрибуты и параметр записывайте одной строкой: указывайте target `property:` один раз и перечисляйте атрибуты через запятую. Например: `[property: Description("Номер страницы"), FromQuery] int Page = 1`.
- Не объединяйте в одну секцию атрибуты с разными target и не меняйте порядок атрибутов, если он влияет на поведение фреймворка.

## Валидация запросов и моделей

- Все входные данные валидируйте через FluentValidation. Валидатор должен быть объявлен для типа, который фактически привязывается MVC из body, query или form.
- Не внедряйте `IValidator<T>` через `[FromServices]` в action-методы и не вызывайте `Validate` или `ValidateAsync` вручную в контроллерах. Автоматическая FluentValidation сама находит зарегистрированный валидатор, выполняет его для привязанного входного типа и формирует ответ с ошибками валидации.
- Не дублируйте в контроллере обработку результата валидации и не вызывайте handler, если автоматическая валидация уже отклонила запрос: этот поток обрабатывается настроенной инфраструктурой до выполнения action.
- Валидатор может относиться не только к `ICommand` или `IQuery`, но и к промежуточной DTO/model. Если одна модель используется и при создании, и при обновлении, общие правила размещайте в валидаторе этой модели, чтобы не дублировать их в командах.
- Правила, специфичные только для одной операции, оставляйте в валидаторе соответствующей команды или запроса.
- Для проверок, зависящих от базы данных, используйте асинхронные правила FluentValidation и передавайте `CancellationToken` в EF Core.
- Для одного поля создавайте один блок `RuleFor` или `RuleForEach`; не повторяйте `RuleFor` для одной и той же property. Несколько проверок этого поля объединяйте в одну цепочку.
- Каждую пару «проверка + `WithMessage`» размещайте рядом, желательно на одной строке, чтобы было однозначно видно, к какой проверке относится сообщение. Если следующую проверку нельзя выполнять после ошибки предыдущей, начинайте цепочку с `Cascade(CascadeMode.Stop)`.
- Условную проверку оформляйте в порядке `Validator(...).When(...).WithMessage(...)`. В цепочке с несколькими валидаторами явно используйте `ApplyConditionTo.CurrentValidator`, если условие относится только к непосредственно предшествующей проверке.
- Сообщения валидации, возвращаемые клиенту, пишите на русском языке и формулируйте в терминах предметной области.

## Интерфейсы и абстракции

- Не создавайте интерфейс для каждого класса по умолчанию. Интерфейс вводите, когда он отделяет потребителя от инфраструктуры или когда действительно нужны несколько взаимозаменяемых реализаций.
- Для отдельного прикладного или инфраструктурного слоя интерфейс является оправданной границей: фичи и другие потребители должны зависеть от контракта слоя, а не от его конкретной реализации.
- Не добавляйте интерфейсы исключительно ради моков: отдельные UI- или интеграционные тестовые реализации в этом проекте не являются основанием для дополнительной абстракции.
- Стандартные CQRS-контракты `IQuery`, `ICommand` и их handlers являются частью принятой архитектуры и используются независимо от этого ограничения.

## Миграции базы данных

- Добавляйте и удаляйте миграции только инструментами Entity Framework Core (`dotnet ef migrations add`, `dotnet ef migrations remove`); не создавайте и не удаляйте migration, designer или snapshot-файлы вручную.
- Не редактируйте вручную содержательную часть сгенерированных EF Core migrations, designer-файлов и model snapshot. Допустимы только механические изменения форматирования, необходимые для соответствия `.editorconfig`, без изменения операций миграции и модели.
- Если сгенерированная миграция неверна, удалите её инструментом EF Core, исправьте модель сущностей или EF-конфигурацию и сгенерируйте миграцию заново вместо ручной правки файлов миграции.
- AI-агент не должен выполнять миграции на какой-либо базе данных (`dotnet ef database update` и аналогичные команды).
- Все миграции пользователь применяет вручную.
- После создания миграции агент должен проверить сборку проекта и сообщить пользователю имя созданной миграции.

## Именование DTO и схемы OpenAPI

- Все DTO, которые попадают в OpenAPI, должны иметь уникальные короткие имена во всём API-проекте. Разные namespace не считаются достаточным различием.
- Ответ list/get-all endpoint оформляйте объектом-обёрткой, а его основную коллекцию называйте `Items`, независимо от типа возвращаемых сущностей. Не называйте основную коллекцию `Materials`, `Categories` и другими предметными именами; дополнительные вспомогательные коллекции могут иметь предметное имя.
- Все описания эндпоинтов, параметров, полей DTO и ответов, отображаемые в OpenAPI/Scalar, должны быть написаны на русском языке. Для публичных полей DTO и параметров явно задавайте русскоязычный атрибут `Description`, не полагаясь на автоматически сформированное описание.
- Каждый query-параметр, каждое поле входящего request body и каждое поле исходящего response body обязаны иметь явный атрибут `Description` с описанием на русском языке. Это правило распространяется также на поля вложенных DTO и элементы составных моделей запросов и ответов.
- Атрибут `Description` задавайте непосредственно на том параметре или property, который попадает в OpenAPI-схему. Наличие описания у содержащего DTO, action-метода или ответа не заменяет описание его отдельных полей.
- Имя C# property или параметра должно соответствовать имени этого значения во входящем запросе и исходящем ответе с учётом стандартной политики именования приложения. Например, если в JSON или query используется `start`, свойство также должно называться `Start`, а не `Begin` с дополнительным переименованием.
- Не используйте атрибуты и настройки, меняющие имя при сериализации, десериализации или model binding: `JsonPropertyName`, `FromQuery(Name = ...)`, `FromRoute(Name = ...)`, `FromForm(Name = ...)` и их аналоги. Если внешнее имя требуется изменить, переименуйте саму C# property или параметр, чтобы одно согласованное имя использовалось во всех направлениях преобразования данных.
- Не создавайте два публичных DTO с одинаковым именем типа: генератор OpenAPI может использовать короткое имя как идентификатор `components.schemas`, из-за чего одна схема подменит другую или получит свойства другого DTO.
- Имя DTO должно отражать контекст использования. Вместо общего `SheetSizeDto` для вложенного размера материала используйте `MaterialSheetSizeDto`; аналогично добавляйте предметный префикс к другим потенциально совпадающим DTO.
- Перед добавлением или переименованием DTO выполните поиск по короткому имени во всём API-проекте и убедитесь, что коллизий нет.
- После изменения публичного DTO проверьте сгенерированный `/swagger/v1/swagger.json`: отдельная схема должна иметь ожидаемое имя, свойства, типы и список `required`.

## Тестирование

- Стабильные сценарии ручного тестирования находятся в `catalog-api/docs/TEST_CASES.md`. Не добавляйте туда результаты конкретных прогонов, даты, временные блокировки и найденные дефекты.
- Не выполняйте полный прогон сценариев из `catalog-api/docs/TEST_CASES.md` после каждой правки. Запускайте эти тест-кейсы только по отдельной просьбе разработчика.
- Перед функциональным HTTP-прогоном обязательно проверьте порт Catalog API, выбранный для запуска (по умолчанию `5005`). Если порт занят, немедленно прекратите прогон и сообщите пользователю. Без прямого указания пользователя запрещено останавливать занимающий порт процесс, использовать уже запущенный на нём API или самостоятельно выбирать другой порт/endpoint.
- Перед функциональным прогоном проверьте соответствие отслеживаемых текстовых файлов правилам корневого `.editorconfig`, включая форматирование C#, кодировку UTF-8 без BOM и окончания строк LF.
- `catalog-api/docs/TEST_EXECUTION.md` должен содержать только результат последнего прогона. При новом прогоне полностью заменяйте предыдущий отчёт; историю прогонов в этом файле не накапливайте.
- Для DEV-контура можно отключать проверку TLS-сертификата, например через `curl --insecure`. Для production-контура проверку TLS не отключайте.
- Для DEV-авторизации используйте служебные данные из `mm-accounts-api/accounts-api/docs/TEST_CREDENTIALS.md`.
- Не сохраняйте в документации значения cookie, токены и другие полученные секреты.
- Перед авторизованными сценариями получите `AccountsApiCookie` через Accounts API. Если авторизация или Accounts API недоступны, не выполняйте зависимые сценарии и зафиксируйте блокировку в `TEST_EXECUTION.md`.
- Основные функциональные сценарии и очистку тестовых данных выполняйте только с cookie тестера. Не используйте cookie менеджера или администратора как авторизацию по умолчанию: они допустимы только для ролевых проверок и изолированных сценариев `HIST-01—HIST-12` с отдельным уникальным префиксом. После основного прогона убедитесь, что его префикс не создал записей истории.
- Для `HIST-01—HIST-12` используйте уникальный положительный целочисленный `runId`, а во все названия тестовых сущностей включайте маркер `codex-history-{runId}`. После проверок обязательно вызовите tester-only endpoint `DELETE /api/catalog/history/test-runs/{runId}`, проверьте точное число удалённых событий и нулевую выдачу по маркеру этого прогона. Не сравнивайте глобальный `totalCount`, поскольку история может пополняться параллельно.
- После тестового прогона удаляйте созданные тестовые сущности и временные файлы.

## Дефекты

- Подтверждённые проблемы регистрируйте в `catalog-api/docs/DEFECTS.md`.
- Один дефект оформляйте одной записью с постоянным идентификатором `DEF-###`.
- В `TEST_EXECUTION.md` указывайте идентификатор связанного дефекта.
- После исправления и успешного ретеста удаляйте подробную запись из раздела «Открытые дефекты» и добавляйте в «Историю исправлений» краткую строку `DEF-### исправлен`.
- Не переносите в историю полное описание, шаги и результаты исправленного дефекта.
