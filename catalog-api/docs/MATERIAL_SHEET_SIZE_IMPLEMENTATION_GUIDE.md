# MaterialSheetSize: принятые решения и аналогия для производителей

Документ фиксирует итоговые требования к функциональности размеров материалов и служит образцом для реализации справочника производителей.

## MaterialSheetSize

### Модель данных

Сущность `MaterialSheetSize` хранится в таблице `catalog.material_sheet_sizes` и содержит:

- `Id` — идентификатор;
- `Name` — обязательное название длиной не более 100 символов;
- `Height` — обязательная положительная высота;
- `Width` — обязательная положительная ширина;
- `OrderByCol` — порядок отображения;
- коллекцию связанных материалов.

Материал содержит обязательный внешний ключ `MaterialSheetSizeId`. Удаление размера, который используется материалами, запрещено. Для внешнего ключа используется `DeleteBehavior.Restrict`.

Пара `Height + Width` защищена уникальным индексом в базе. Одинаковые габариты нельзя создать даже с другим названием.

Название также проверяется на уникальность в командах создания и редактирования, но отдельного уникального индекса по `Name` в базе нет.

### API

Базовый маршрут контроллера:

```text
/api/materials/sheet-sizes
```

Методы:

- `GET /api/materials/sheet-sizes` — публичный список;
- `GET /api/materials/sheet-sizes/{id}` — публичная карточка;
- `POST /api/materials/sheet-sizes` — создание;
- `PUT /api/materials/sheet-sizes/{id}` — редактирование;
- `DELETE /api/materials/sheet-sizes/{id}` — удаление;
- `POST /api/materials/sheet-sizes/change-order-col` — перемещение вверх или вниз.

Названия методов контроллера соответствуют сущности, а не техническим операциям `GetAll`/`GetById`:

- `MaterialSheetSizes`;
- `MaterialSheetSize`;
- `CreateMaterialSheetSize`;
- `UpdateMaterialSheetSize`;
- `DeleteMaterialSheetSize`;
- `ChangeOrderCol`.

GET-методы доступны анонимно. Изменяющие методы требуют cookie-аутентификацию.

### OpenAPI

Для контроллера и каждого метода должны сохраняться используемые в проекте атрибуты документации:

- `OpenApiTagOrder`;
- `EndpointSummary`;
- `EndpointDescription`;
- `ProducesResponseType` с типом, кодом, media type и описанием;
- `Description` для route-, query- и body-параметров;
- описание ответа `401 Unauthorized` на контроллере.

Порядок тегов раздела материалов:

1. материалы — `OpenApiTagOrder(1)`;
2. категории материалов — `OpenApiTagOrder(2)`;
3. размеры материалов — `OpenApiTagOrder(3)`.

### DTO и наименование

В самостоятельном API размеров используется `SheetSizeDto`:

```json
{
  "id": 3,
  "name": "ЛДСП",
  "height": 2750,
  "width": 1830,
  "orderByCol": 3
}
```

В контракте материала размер возвращается вложенным объектом `sheetSize`, но без `orderByCol`:

```json
{
  "sheetSize": {
    "id": 3,
    "name": "ЛДСП",
    "height": 2750,
    "width": 1830
  }
}
```

Правило: `orderByCol` возвращается у сущности, являющейся главным элементом запрошенного списка. Сортировка вложенных связанных объектов в контракт не выносится.

В DTO, уже находящемся в контексте материала, не нужно повторять слово `Material`. Поэтому используются имена `SheetSize`, `SheetSizeId`, `Category`, а не `MaterialSheetSize`, `MaterialSheetSizeId` и `MaterialCategory` в JSON-контракте.

Пользовательские описания и ошибки используют формулировку «размер материала». Термин `MaterialSheetSize` остаётся техническим названием сущности, а слово «плитный» не дублируется в сообщениях API.

### Создание и редактирование

Модель принимает:

```json
{
  "name": "ЛДСП",
  "height": 2750,
  "width": 1830
}
```

Проверки:

- `Name` обязателен;
- длина `Name` — не более 100 символов;
- `Height > 0`;
- `Width > 0`;
- название не должно повторяться;
- пара `Height + Width` не должна повторяться;
- при редактировании текущая запись исключается из проверок уникальности.

Новая запись получает `OrderByCol = max(OrderByCol) + 1`.

### Сортировка

Список всегда сортируется по `OrderByCol`.

Команда изменения порядка принимает:

```json
{
  "id": 3,
  "direction": "UP"
}
```

Поддерживаются направления `UP` и `DOWN`. Запись меняется значением `OrderByCol` с соседней записью. Перемещение первого элемента вверх и последнего элемента вниз возвращает `400 Bad Request`. Обмен выполняется в транзакции с временным уникальным значением, чтобы не нарушить уникальный индекс `OrderByCol`.

### Миграции

Нормализация размеров и добавление названия разделены, потому что первая миграция уже была применена:

- `NormalizeMaterialSheetSizes` — создаёт таблицу размеров, переносит габариты и связи материалов, удаляет старую строковую колонку размера;
- `AddMaterialSheetSizeName` — добавляет nullable `name`, заполняет существующие строки значением вида `2750×1830`, затем устанавливает `NOT NULL`.

Применённые миграции изменять нельзя. Новые изменения схемы оформляются следующими миграциями. AI-агент не применяет миграции к базе, а только создаёт их, проверяет сборку и сообщает имя.

## Постановка для следующего агента: производители

Нужно реализовать справочник производителей по аналогии с `MaterialSheetSize`.

Требуется:

1. Создать сущность и таблицу производителей с полями `Id`, `Name`, `OrderByCol` и связью с материалами.
2. Добавить обязательный `ManufacturerId` в материал и навигационное свойство.
3. Реализовать публичные GET и защищённые POST, PUT, DELETE.
4. Запретить удаление производителя, используемого материалами, через `DeleteBehavior.Restrict` и понятную ошибку API.
5. Проверять обязательность и уникальность названия. Перед добавлением индекса отдельно согласовать, должна ли уникальность имени обеспечиваться только командой или также базой.
6. Нового производителя добавлять в конец: `max(OrderByCol) + 1`.
7. Реализовать `POST .../change-order-col` с `UP`/`DOWN`, обменом соседних значений в транзакции и проверками границ.
8. В отдельном списке производителей возвращать `orderByCol`.
9. В материале возвращать вложенный объект:

   ```json
   "manufacturer": {
     "id": 1,
     "name": "Производитель"
   }
   ```

   Во вложенном объекте производителя `orderByCol` не возвращать.

10. В моделях создания и редактирования материала принимать `manufacturerId`.
11. Убрать линейные поля производителя из DTO материала, если они появятся; использовать единый вложенный объект в публичных и административных ответах.
12. Соблюсти стиль имён методов контроллера и полный набор OpenAPI-атрибутов, описанный выше.
13. Назначить производителям следующий свободный `OpenApiTagOrder` после размеров материалов, если пользователь не задаст иной порядок.
14. Подготовить EF Core migration, но не применять её к базе.
15. Обновить стабильные сценарии в `docs/TEST_CASES.md` и HTTP regression runner: CRUD, дубли, связь с материалом, запрет удаления используемой записи, сортировка вверх/вниз, публичный доступ к GET и `401` для анонимных изменений.

Перед реализацией миграции необходимо определить, какие производители должны быть назначены уже существующим материалам. Если достоверно вывести производителя из текущих данных нельзя, не назначать его автоматически по догадке: подготовить безопасную поэтапную миграцию или запросить явное правило сопоставления.
