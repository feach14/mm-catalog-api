# Тест-кейсы Catalog API

## Контекст

- Авторизация выполняется через Accounts API. Учётные данные и правила выбора пользователя находятся в `mm-accounts-api/accounts-api/docs/TEST_CREDENTIALS.md`.
- Все основные функциональные сценарии и очистка тестовых данных выполняются только тестером. Cookie менеджера или администратора не может быть cookie по умолчанию; она используется только в ролевых проверках и изолированных `HIST-01—HIST-12`.
- Изолированные сценарии истории используют отдельный уникальный префикс. После основного прогона по его префиксу не должно быть ни одной записи истории; события `HIST-01—HIST-12` проверяются только по своему префиксу.
- Публичные чтения: материалы, категории, карточки и изображения.
- Авторизация cookie требуется для чтений административной панели и всех изменений данных.
- Все enum в JSON передаются и возвращаются строковыми именами, а не числами: например, `"direction": "UP"` и `"countTypeEnum": "M2"`.
- Проверки выполняются только через HTTP API. Состояние считается корректным по кодам ответа и данным, доступным через endpoints.
- После физического удаления материал недоступен через публичную и административную карточки.

## CODE — соответствие EditorConfig

Проверки выполняются перед функциональным HTTP-прогоном. Требования корневого `.editorconfig` распространяются на все отслеживаемые текстовые файлы основного репозитория и submodule `core`.

| ID | Сценарий | Шаги | Ожидаемый результат |
|---|---|---|---|
| CODE-01 | Форматирование .NET-кода | Выполнить `dotnet format catalog-api/catalog-api.slnx --verify-no-changes --no-restore` | Команда завершается с кодом `0`; C#-файлы соответствуют `.editorconfig` |
| CODE-02 | Кодировка и окончания строк | Проверить все отслеживаемые текстовые файлы основного репозитория и `core` | Все файлы являются валидным UTF-8 без BOM, используют LF и не содержат CR/CRLF |

## Фиксация результата прогона

- `catalog-api/docs/TEST_EXECUTION.md` содержит только результат последнего прогона.
- При новом прогоне предыдущий отчёт полностью заменяется; история прогонов в файле не ведётся.
- В отчёте указываются среда, инструмент, результаты групп сценариев, связанные дефекты и результат очистки тестовых данных.

## Автоматизированный HTTP-прогон

- Автоматизированная часть сценариев запускается командой `python3 catalog-api/http_regression_runner.py` из корня репозитория.
- Раннер работает только через HTTP-интерфейсы Accounts API и Catalog API, самостоятельно запускает и перезапускает локальный Catalog API и удаляет созданные тестовые сущности.
- Раннер обязан установить cookie тестера как cookie по умолчанию до создания любых тестовых сущностей. Отдельные ролевые проверки используют cookie обычного пользователя, тестера, менеджера и администратора; изолированные проверки создания истории используют менеджера или администратора и отдельный префикс.
- Для `HIST-01—HIST-12` раннер создаёт отдельный положительный целочисленный `runId` и включает маркер `codex-history-{runId}` во все названия тестовых сущностей. После всех проверок раннер вызывает от имени тестера `DELETE /api/catalog/history/test-runs/{runId}`, проверяет число удалённых записей и нулевую выдачу по маркеру прогона.
- Глобальный `totalCount` истории не сравнивается: параллельные реальные изменения каталога не должны приводить к ложному провалу тестов.
- Раннер хранится в репозитории как рабочая история и вспомогательный инструмент. ИИ-агентам разрешено без дополнительных согласований исправлять, расширять и актуализировать его вместе с изменениями тест-кейсов и API.
- Перед запуском должны быть собраны проекты и запущен локальный Accounts API на порту `5003` (либо по адресу из `ACCOUNTS_API_URL`) на том же контуре базы данных и Data Protection, что и Catalog API; Catalog API на порту `5005` должен быть свободен.
- Перед стартом раннер обязан проверить порт Catalog API, выбранный для прогона (по умолчанию `5005`). Если порт занят, прогон немедленно прекращается до запуска Catalog API и создания тестовых данных. Агент не должен останавливать существующий процесс, выполнять тесты через уже запущенный API или самостоятельно выбирать другой порт/endpoint. Продолжить на другом порту можно только после прямого указания пользователя с конкретным портом или `CATALOG_API_URL`.

## IMG — загрузка изображений

Все загруженные в ходе прогона изображения должны быть последовательно использованы в сценариях создания и обновления тестового материала. Проверяется только наблюдаемое поведение HTTP API. После завершения сценариев ни один тестовый GUID не должен возвращать изображение через API.

| ID | Сценарий | Шаги | Ожидаемый результат |
|---|---|---|---|
| IMG-01 | Доступ к загрузке | Отправить `POST /api/materials/images` без cookie | `401 Unauthorized` |
| IMG-02 | Допустимые форматы | Загрузить PNG, JPEG и WebP через multipart-поле `file`, передав `imageType=Original` | Для каждого файла `200 OK`; возвращены GUID и корректный `contentType` |
| IMG-03 | Валидация загрузки | Отправить пустой, слишком большой или неподдерживаемый файл | `400 Bad Request` с понятной ошибкой |
| IMG-04 | Доступность загруженных файлов | Запросить PNG, JPEG и WebP через `GET /api/materials/images/{fileGuid}` до привязки к материалу | Для каждого GUID получен `200 OK`, корректный `Content-Type`, байты совпадают с исходным файлом |
| IMG-05 | Загруженный файл переживает перезапуск | Перезапустить API и вызвать `GET /api/materials/images/{fileGuid}` для PNG из `IMG-02` | `200 OK`, корректный `Content-Type`, файл совпадает с исходным |
| IMG-06 | Создание материала после перезапуска | После перезапуска передать GUID PNG из `IMG-02` при создании материала | Материал создан; GUID PNG указан в карточке материала |
