# Тест-кейсы Catalog API

## Контекст

- Авторизация выполняется через Accounts API. Учётные данные и правила выбора пользователя находятся в `mm-accounts-api/accounts-api/docs/TEST_CREDENTIALS.md`.
- Все основные функциональные сценарии и очистка тестовых данных выполняются только тестером. Cookie менеджера или администратора не может быть cookie по умолчанию; она используется только в ролевых проверках и изолированных `HIST-01—HIST-12`.
- Изолированные сценарии истории используют отдельный уникальный префикс. После основного прогона по его префиксу не должно быть ни одной записи истории; события `HIST-01—HIST-12` проверяются только по своему префиксу.
- Публичные чтения: материалы, карточки, изображения и параметры материала для Calculate по Id.
- Авторизация cookie требуется для чтений административной панели и всех изменений данных.
- Все enum в JSON передаются и возвращаются строковыми именами, а не числами: например, `"direction": "UP"` и `"countTypeEnum": "M2"`.
- Проверки выполняются только через HTTP API. Состояние считается корректным по кодам ответа и данным, доступным через endpoints.
- После физического удаления материал недоступен через публичную и административную карточки.
- Сортировка по `OrderByCol` использует только это поле. При одинаковых значениях взаимный порядок записей не проверяется; для сценариев перестановки предварительно задаётся сохранённый порядок.

## CODE — соответствие EditorConfig

Проверки выполняются перед функциональным HTTP-прогоном. Требования корневого `.editorconfig` распространяются на все отслеживаемые текстовые файлы основного репозитория и submodule `core`.

| ID | Сценарий | Шаги | Ожидаемый результат |
|---|---|---|---|
| CODE-01 | Форматирование .NET-кода | Выполнить `dotnet format catalog-api/catalog-api.slnx --verify-no-changes --no-restore` | Команда завершается с кодом `0`; C#-файлы соответствуют `.editorconfig` |
| CODE-02 | Кодировка и окончания строк | Проверить все отслеживаемые текстовые файлы основного репозитория и `core` | Все файлы являются валидным UTF-8 без BOM, используют LF и не содержат CR/CRLF |

## Фиксация результата прогона

- `catalog-api/docs/TEST_EXECUTION.md` содержит только результат последнего прогона.
- При новом прогоне предыдущий отчёт полностью заменяется; история прогонов в файле не ведётся.
- В отчёте указываются среда, инструмент, результаты групп сценариев, связанные дефекты и результат очистки тестовых данных.

## Автоматизированный HTTP-прогон

- Автоматизированная часть сценариев запускается командой `python3 catalog-api/http_regression_runner.py` из корня репозитория.
- Целевая проверка `SearchText` запускается отдельно: `python3 catalog-api/http_regression_runner.py --material-search`. Она выполняет только `SEARCH-02`, `SEARCH-09—SEARCH-15` и очистку собственных данных; полный прогон не запускается. Требования DEV-окружения, свободного порта, предварительной сборки и применения миграции сохраняются. Авторизация — только тестером; существующие справочники не изменяются.
- Раннер работает только через HTTP-интерфейсы Accounts API и Catalog API, самостоятельно запускает и перезапускает локальный Catalog API и удаляет созданные тестовые сущности.
- Раннер обязан установить cookie тестера как cookie по умолчанию до создания любых тестовых сущностей. Отдельные ролевые проверки используют cookie обычного пользователя, тестера, менеджера и администратора; изолированные проверки создания истории используют менеджера или администратора и отдельный префикс.
- Для `HIST-01—HIST-12` раннер создаёт отдельный положительный целочисленный `runId` и включает маркер `codex-history-{runId}` во все названия тестовых сущностей. После всех проверок раннер вызывает от имени тестера `DELETE /api/for-admin/catalog/history/test-runs/{runId}`, проверяет число удалённых записей и нулевую выдачу по маркеру прогона.
- Глобальный `totalCount` истории не сравнивается: параллельные реальные изменения каталога не должны приводить к ложному провалу тестов.
- Раннер хранится в репозитории как рабочая история и вспомогательный инструмент. ИИ-агентам разрешено без дополнительных согласований исправлять, расширять и актуализировать его вместе с изменениями тест-кейсов и API.
- Прогон выполняется только в DEV: Accounts API — `https://accounts-api.debug.feach.ru:5003`, Catalog API — `https://catalog-api.debug.feach.ru:5005`; PostgreSQL — `Host=185.151.240.63;Port=5432;Database=mm-debug`. Перед запуском должны быть собраны оба проекта; Accounts API должен быть запущен с указанными ниже явными переменными окружения, порт Catalog API `5005` должен быть свободен.
- Перед стартом раннер обязан проверить порт Catalog API `5005`. Если порт занят, прогон немедленно прекращается до запуска Catalog API и создания тестовых данных. Агент не должен останавливать существующий процесс, выполнять тесты через уже запущенный API или самостоятельно выбирать другой порт/endpoint. Другой DEV-порт или endpoint допускается только по прямому указанию пользователя с конкретным адресом и соответствующей актуализацией ограничений раннера.

Для запуска нужен .NET 10. DEV-настройки авторизации, адресов и БД передаются явно через окружение: выбор `Development` сам по себе не подтверждает DEV-БД. Значения этих параметров в `appsettings.Development.json` не используются как основание для выбора контура. Раннер должен отказать до запуска Catalog API и создания данных, если обязательные переменные отсутствуют либо указывают на адреса или БД вне указанного DEV-контура.

Секреты экспортируйте из менеджера секретов или локального файла вне Git, отдельно в каждом терминале запуска. Такой файл должен задавать следующие переменные; приведённые значения являются placeholders:

```sh
export ACCOUNTS_DEV_DB_USERNAME='<пользователь БД Accounts DEV>'
export ACCOUNTS_DEV_DB_PASSWORD='<пароль БД Accounts DEV>'
export CATALOG_DEV_DB_USERNAME='<пользователь БД Catalog DEV>'
export CATALOG_DEV_DB_PASSWORD='<пароль БД Catalog DEV>'
export CATALOG_DEV_DP_USERNAME='<пользователь хранилища Data Protection DEV>'
export CATALOG_DEV_DP_PASSWORD='<пароль хранилища Data Protection DEV>'
```

Реальные `Username`/`Password`, полные строки подключения, cookie и токены не сохраняйте в репозитории, отчёте или выводе команд. Пользователи и пароли трёх подключений могут различаться. Catalog API использует отдельные `DbConnString` и `DataProtectionDbConnString`; Accounts API использует свой `DbConnString` также для Data Protection. Все подключения должны вести в `mm-debug`, а хранилище ключей Catalog API — в то же DEV-хранилище, где Accounts API защищает cookie.

В каждом терминале из корня `mm-catalog-api` загрузите свой внешний файл секретов, заменив пример пути, и задайте общий DEV-контекст:

```sh
source '/absolute/path/outside-git/catalog-dev-secrets.env'
export ASPNETCORE_ENVIRONMENT=Development
export ACCOUNTS_API_URL=https://accounts-api.debug.feach.ru:5003
export CATALOG_API_URL=https://catalog-api.debug.feach.ru:5005
export Cookie__DomainName=.debug.feach.ru
export Cookie__CookieName=AccountsApiCookie
export Cors__DomainName=debug.feach.ru
export DbConnString="Host=185.151.240.63;Port=5432;Database=mm-debug;Username=${CATALOG_DEV_DB_USERNAME};Password=${CATALOG_DEV_DB_PASSWORD}"
export DataProtectionDbConnString="Host=185.151.240.63;Port=5432;Database=mm-debug;Username=${CATALOG_DEV_DP_USERNAME};Password=${CATALOG_DEV_DP_PASSWORD}"
```

Соберите Catalog API и Accounts API из корня `mm-catalog-api`; пример предполагает соседние каталоги репозиториев:

```sh
dotnet build catalog-api/catalog-api.slnx
dotnet build ../mm-accounts-api/accounts-api/accounts-api.slnx
```

В отдельном терминале проверьте порт Accounts API `5003` перед собственным запуском. Не останавливайте процесс пользователя и не меняйте порт самостоятельно. Уже запущенный Accounts API можно использовать только после проверки его DEV-адреса, БД и настроек cookie; если подтвердить контур нельзя, зафиксируйте блокировку. Собственный Accounts API запускайте без launch profile, чтобы профиль не подменил переданные адрес и окружение:

```sh
ASPNETCORE_URLS="$ACCOUNTS_API_URL" \
DbConnString="Host=185.151.240.63;Port=5432;Database=mm-debug;Username=${ACCOUNTS_DEV_DB_USERNAME};Password=${ACCOUNTS_DEV_DB_PASSWORD}" \
dotnet run --project ../mm-accounts-api/accounts-api/Accounts.Api/Accounts.Api.csproj --no-launch-profile --no-build
```

В терминале Catalog API с тем же общим DEV-контекстом выполните предварительные проверки CODE, затем запустите раннер. Catalog API отдельно не запускайте: раннер запускает и перезапускает собственный процесс с `ASPNETCORE_ENVIRONMENT=Development`, `ASPNETCORE_URLS=$CATALOG_API_URL` и явно экспортированными DEV-подключениями.

```sh
ASPNETCORE_URLS="$CATALOG_API_URL" python3 catalog-api/http_regression_runner.py
```

После прогона проверьте очистку созданных тестовых сущностей и временных файлов. Раннер останавливает собственный Catalog API также при ошибке; собственный Accounts API после работы остановите в его терминале. Процессы пользователя не останавливайте. В отчёте фиксируйте DEV-адреса и целевую БД без секретов, результат проверки контура и очистки.

## AUTH — доступ

Публичное чтение материалов и изображений использует `/api/materials/...`. Категории доступны через административные endpoints; контракт для Calculate возвращает категорию внутри каждого материала. Административные списки и карточки, создание, изменение, удаление, сортировка и загрузка изображений используют `/api/for-admin/materials/...` и требуют cookie пользователя с ролью `manager`, `admin` или `tester`.

|---|---|---|---|

## SEARCH — поиск и пагинация

Запросы выполняются анонимно к `GET /api/materials/search`. Создать тестером пять материалов с уникальным общим маркером в названии: A/B/C/D/E (латинские суффиксы для проверки сортировки), разными артикулами, двумя категориями, производителями, размерами и толщинами, количеством 0 и 1 и разными вариантами использования материала.
